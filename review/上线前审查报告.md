## Free 计划补充与本次修订

用户明确要求“能省则省”。因此本报告按最少新增存储、读写和基础设施来选择修复方案；容量风险不等于现在已经出现资源不足。

截图为账户级 D1 汇总：2/10 个数据库、读取 390/5,000,000 行、写入 786/100,000 行、总存储 242.49MB/5GB。读取和写入分别只占截图额度的 0.0078% 和 0.786%。另一张列表中 `bengbeng_bomb` 的大小约 139.26kB；其余两列缺少表头，不解释为确定的指标。账户总存储不可全归因于本项目，截图时刻用量也不能预测宣传后的每日需求。

官方当前 D1 Free 为每天读取 500 万行、写入 10 万行，账户总存储 5GB；额度按行而非 SQL 次数计量，索引也会增加写入成本，达到每日读写上限后查询会报错。每次完成包含多条 SQL，不代表每人只写一行。以返回的 `meta.rows_read / rows_written` 和控制台统计衡量，不能将每日本次写入额度直接换算成可支持人数。[D1 官方计费说明](https://developers.cloudflare.com/d1/platform/pricing/)

Workers Free 动态请求额度为每天 10 万次；直接静态资源请求免费且不限次数，Pages Functions 同样计入 Workers 配额。现有 `run_worker_first` 仅匹配 API 的方向应保留。模型/WASM 大主要影响用户下载和手机体验，不应直接定性为会耗尽 Worker 动态请求配额。[Workers 计费](https://developers.cloudflare.com/workers/platform/pricing/)、[静态资源计费](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)、[Pages Functions 计费](https://developers.cloudflare.com/pages/functions/pricing/)

**调整后的方案选择：**
- 保留无状态签名二维码；优先精简签名载荷、加长度预算，短链接查库降为可选折中。验签仍有 CPU 成本，但避免为每条分享新增 metadata 存储与打开时查库。
- 群组恢复优先用稳定 groupId 关联浏览器本地参与记录，复用既有服务端鉴权，不新增恢复表。
- 单人删除后的重玩行为需明确产品语义。若“只删除私人结果，未过期邀请仍可重新参与”是有意设计，则该项改为已知取舍，不强制加撤销表；若承诺销毁链接/一次性参与，才需要保留到期的最小撤销标记。不能同时保证立即完全无状态和可靠逐链接撤销。
- 聚合表属于用额外写入换读取。先合并重复聚合、减少无变化 UPDATE；有真实额度证据后再决定是否新增表及索引。
- 维持按需读取，不为了“实时”增加高频轮询；不默认引入 KV、Durable Objects、持久队列或数据库限流计数。
- 凭证隔离、响应正文超时、分 P、截图文案仍应修复；Free 约束不改变这些问题的正确性。

## 用户截图：QAQ 的 12 秒并没有丢失

截图显示：挑战次数 1、绷住人数 1、失败比例 0%、平均坚持时间 12.0 秒；参与列表也记录 QAQ 全程绷住 12.0 秒。四项统计与参与记录相符。

`src/client/app/Settlement.tsx:105–130` 仅根据失败时间柱状图是否为空显示统一文案，空时始终说“还没有人记录没绷住的时间，你是第一批挑战者”。`src/worker/repositories/groups.ts:235–246` 的分桶 SQL 只选 `outcome='failed'`，因此全程成功本来就不会产生失败时间。

已用真实 SQLite、仓库迁移和仓库 Repository 复现 QAQ 成功 12 秒：得到 `total=1, held=1, failed=0, averageElapsedSeconds=12, buckets=[]`，参与列表仍含 QAQ 与 12 秒。属于 **P2 展示文案没有区分状态，不是这张截图所显示的数据丢失**；这不等于直接查询确认了三天前的生产记录。

建议空态分成：
- `total===0`：还没有完成记录，来做第一位挑战者。
- `total>0 && failed===0`：已有 X 次挑战全部绷住，暂无失败时间分布。
- `failed>0` 但没有有效分桶：暂无失败时间分布数据。不要继续声称没人失败。

## 优先修复的问题

### 1. P1：全站分析脚本与链接权限凭证混用

位置：`index.html:10–16`；`src/client/app/ManageView.tsx:8–9`；`src/worker/index.ts:95–106`。

所有页面无条件加载 Clarity，管理页依靠 `/manage#m=...` 的令牌授予读取、结束和删除权限。挑战、群组、战报的令牌也直接放在路径里。URL fragment 不会随普通 HTTP 请求发送，但页面内运行的第三方 JavaScript 可以读取它。

微软当前公开实现中，Clarity 读取 `location.href` 作为 URL 元数据；URL 清理函数按配置处理问号后的指定参数，不自动移除路径令牌或本项目 `#m=` fragment。因此本项目没有在收集前建立可靠的凭证隔离边界。线上 HTML 包含该脚本，线上 bootstrap 的哈希也与 CSP 允许值一致。这里只做了代码和 HTTP 核对，**没有抓取真实用户的 Clarity 上报，也没有访问 Clarity 控制台，因此不声称已经证实历史凭证外传**。

影响：在默认采集路径下，能读取分析数据的人可能取得仍有效的管理链接，查看或删除他人的结果。`Referrer-Policy: no-referrer` 不会阻止脚本主动读取地址。

建议优先在含凭证的流程彻底停用第三方会话录制；如保留访问统计，使用不携带凭证的路由类别。必须覆盖从首页进入挑战的 SPA 导航，不能只在首次加载判断 pathname。DOM 中分享链接的 href 和已有脚本状态也要纳入验证。

依据：[Clarity metadata 源码](https://github.com/microsoft/clarity/blob/master/packages/clarity-js/src/data/metadata.ts)、[URL scrub 源码](https://github.com/microsoft/clarity/blob/master/packages/clarity-js/src/core/scrub.ts)。

### 2. P1（部署条件项）：缺少限流 binding 时接口完全放行

位置：`src/worker/security/rateLimit.ts:21`；`wrangler.jsonc`；`src/worker/index.ts:65–70`。

仓库默认配置没有三个 `RATE_LIMITER_*` binding，本地 Worker dry-run 也没有列出；代码遇到缺失 binding 直接返回 true。这样部署时，公开解析接口、群组参与写入和结果查询均没有应用层频率限制。上游故障时解析重试还会增加请求量。

**这证明仓库默认部署路径缺乏限流，不证明线上控制台没有单独设置 binding 或 WAF 规则。** 本次未访问账号配置，也没有向生产发高频请求来探测阈值。

建议核对生产 `RATE_LIMITER_EXPENSIVE / MUTATION / PUBLIC` 及实际规则，优先复用项目现有 binding 方案，验证当前账号可用配置；先在本地或隔离测试环境验证 429，不强制增加常驻 staging 服务。不要用 D1 每请求写一条计数来实现限流。Worker 内的拒绝仍已触发 Worker 请求，它主要保护后续数据库和上游资源，不能承诺保护全部动态请求额度。缓存/请求合并应有界，内存合并只对当前 isolate 有效，不为此默认引入付费协调服务。不要把每 IP 限流当作排行榜防作弊。

### 3. P2：从同一群组二维码重新进入，无法按旧键恢复未完成挑战

位置：`src/worker/index.ts:30–33,115,139`；`src/client/storage/activeAttempts.ts:67–68,109–112`。

每次解析同一个 entryToken 都为邀请凭证生成新 nonce，因此得到不同 invitationToken。前端恢复记录却以完整 challengeToken 为键精确查找。

复现：同一入口调用两次，groupId 相同、invitationToken 不同。参与者扫码开始后离开，再次扫描原二维码，会用新 token 查找，找不到原来的未完成 attempt；原记录仍在数据库中。刷新原 `/g/<原token>` 页面不等于重新扫码，不应混为同一个场景。

建议群组恢复按稳定 groupId 及本地参与记录建立关联；保留服务端 attemptToken 校验，不要为方便恢复公开参与凭证。另一个方案是为同一入口产生稳定邀请凭证。

### 4. 条件性 P2 / 产品取舍：删除单人结果后，旧挑战链接可以重新计分

位置：`src/worker/repositories/sessions.ts:7–9,75–81`。

单人 destroy 只删除 session 与 trace，没有保留撤销标记；open 对不存在的相同 challenge_id 重新 INSERT。群组已经有 `group_challenge_blocks` 机制，单人没有对应保护。

真实 SQLite 复现：完成一次 → 删除 → 用同一 ID 重新 open/start/complete → 永久统计 total 从 1 变为 2。同一个已完成的单人链接不再保持一次性，管理页也会再次出现新结果。这里不是说旧的私人曲线被恢复，而是旧链接重新创建了新记录。

本项真实复现仍成立，但是否属于缺陷取决于“删除结果”的承诺。若只删除私人结果且允许旧邀请重玩，可接受无撤销记录方案，明确文案及统计规则即可，不应仅为本项强制新增表。若要求删除后禁止再参与，则在用户主动删除时保留到挑战令牌过期的最小撤销标记（不保留昵称或曲线），并在 open/start/complete 的数据库条件中拒绝、测试并发。要计入标记和到期清理的写成本；不为每次打开额外写标记。

### 5. P2：上游超时只覆盖响应头，响应正文可以一直等待

位置：`src/worker/bilibili/adapter.ts:83–93,151–181,219,247`。

fetch 返回响应头后立即 clearTimeout，之后 `reader.read()` 不再受原超时控制。响应头正常但正文停滞时，解析和弹幕处理可超出配置的总时间预算。浏览器 API 包装也在 fetch 返回头部后清理计时器，`response.json()` 同样不在其保护内：`src/client/api/client.ts:60–88`。

已用可控 ReadableStream 与 fake timers 复现：配置 1000ms，上游立即返回 HTTP 200 和 JSON 头部，但 2000ms 后 Promise 仍未结束；继续补齐正文后才完成。

建议保持同一个 deadline/AbortController，直到正文读取和解析完成；超时时取消 reader，上游重试共用预算。要覆盖“已收到头部，正文慢或停住”的测试，而不只测连接超时。

### 6. P2：包含 `?p=2` 的 B 站链接会解析成第 1 P

位置：`src/worker/index.ts:74`；`src/worker/bilibili/adapter.ts:59–63,199–207`。

直接链接解析出 BV 后，上游请求只发送 bvid；URL 上的 p 参数被丢弃，而 API 调用 resolveBilibili 时固定传 1。复现请求 `.../video/BV1234567890/?p=2`，捕获到上游 body 是 `page:1` 且没有原 url。

影响：用户分享第二集/第二分 P，创建的挑战却播放第一集，可能以为网站随机换视频。

建议提取并校验正整数 page，保留到票据、重新解析和转发流程；如果只支持第一 P，至少明确提示，不能静默替换。

### 7. P2：允许的长元数据可让分享二维码生成失败

位置：`src/worker/capabilities/tokens.ts:10,41`；`src/client/app/PublicQrCode.tsx:13–23`；共享 metadata 长度约束。

完整标题、简介、封面 URL、留言被编码进分享凭证，再放进二维码。用各字段允许范围内的合成数据生成群组链接，长度为 3329 字节，当前 qrcode 默认配置明确抛错；组件最终只显示二维码无法生成。

这是长度边界复现，不代表当前每一条真实视频都会失败，也没有对用户截图二维码作扫码成功率测试。即使未超容量，较长链接在 176px 二维码内的识别效果也需要真机检验。

Free 优先方案：保留无状态签名，在签发前设最终 URL 字节/二维码容量预算，精简非必要简介、封面及重复字段，必要时提供精简载荷版本并兼容既有链接。对 UI 必要字段采用明确且可接受的截断/省略策略，超限时在创建阶段解释，不能悄悄生成不可扫码的产物。二维码像素尺寸随模块数量调整，再用手机验证；加大图片尺寸只能改善密度，不能解决超出编码容量。随机短 ID + 服务端 metadata 会增加存储、查询及清理，只作实测证明无状态载荷仍无法满足需求后的可选折中，不再作为首选。

## 数据库与性能结论

- 四个迁移全部在真实内存 SQLite 中执行成功，外键检查通过。顺序重复完成没有重复计数，曲线过期清理正常；群组删除会级联删除参与者且阻止同一群组重建。
- 原有 Repository 测试大量使用 FakeD1，迁移测试中有文本匹配，不能等价于真实 SQL 或 D1 并发验证。本次补足了实际 SQLite SQL 行为，但没有进行生产 D1 写入、并发压力测试、配额评估或远端迁移核对。
- **群组结果分页仍会扫描整个群组的完成记录。** `groups.ts:216–247` 中 resultSummary、groupStats 聚合和失败分桶会在同一结果请求中重复扫描；查询使用了 group/state 索引，并非全库无索引扫描，但 LIMIT 只约束参与者列表，不约束这些聚合。
- 合成的本地 SQLite 数据中，summary + groupStats 的五次中位耗时约为：1000 条 0.4ms、10000 条 5ms、50000 条 约 26–28ms。这只显示随人数增长的趋势，**不是线上 D1 延迟、QPS 或承载上限**。Free 优先顺序是复用 groupStats 中已有的 total/held/failed，取消 resultSummary 的重复汇总，保持鉴权与过期/删除语义；不直接增加长期聚合表。可选短缓存须校验凭证、控制有效期，处理删除失效，不能只按 groupId 无鉴权共享响应。只有实测读额度逼近上限而写额度仍富余，且群组浏览/完成比例支持收益时，才考虑事务内维护 group 级计数与分桶，连同索引维护和清理一起测算。
- 值得优先省写：`sessions.ts:11–12` 的 upsertVideo 每次冲突都 UPDATE，并刷新 updated_at；单人 open 以及群组 open/start 等路径会调用。重复打开已有视频也可能消耗数据库写额度。优先在同一条 UPSERT 中仅对实际 metadata 变化执行 UPDATE，先确认 updated_at 业务语义，不为避免写入而简单增加每次 SELECT。精确节省量以 D1 meta 实测为准。
- 首页初始 JS 672.01kB，gzip 204.61kB；App 静态导入挑战页面，播放器与检测库跟着首页一起加载。这是用户首屏体验优化，降为非阻断项；按路由拆分挑战和结果页面、延迟检测模块不会直接等价于减少 D1 或 Worker 动态调用，也不应以多一次服务器初始化查询为代价。
- 本地模型文件约 3.76MB，WASM 候选约 10.48–11.15MB；正常只加载选中的实现，不能把全部 WASM 大小简单相加为一次下载。文件体积不是 gzip/br 后网络流量。线上静态缓存冒烟通过。
- 推理循环在 requestAnimationFrame 中同步执行 `detectForVideo`，CPU fallback 和低端手机长帧风险尚需真机评估；本次不虚构 FPS 或首屏性能分数。
- `readJson` 先 `request.text()` 再检查字符数，Content-Length 缺失时不是流式字节硬上限。建议补流式读取限制；没有向生产发送大请求验证 DoS。
- 排行榜分数来自客户端结果，不能防主动伪造，README 已有明确限制。娱乐站可接受这一设计，但不宜直接用该数据发奖或作强公平竞赛。

本次浏览器工具启动时遭遇 Windows sandbox ACL 错误（`helper_sandbox_lock_failed / SetNamedSecurityInfoW ... 5`），所以未执行浏览器交互、摄像头、QQ/微信内置浏览器、iOS/Android 播放与完整分享扫码实测。既有测试通过不能替代这些验收。也未访问生产 D1 内容、备份、Cron 执行日志、额度、实际限流配置或 Clarity 项目设置。

## 建议处理顺序

1. 隔离分析脚本与权限凭证；核对线上限流、Cron 和 D1 配额/备份。
2. 采用不新增数据库表的方式修复群组恢复键、正文超时；单人撤销先依产品语义决定是否需要。
3. 修复截图空态、分 P 和长链接分享问题。
4. 进行手机完整流程验收：创建 → 群入口 → 摄像头校准 → 完成 → 结果 → 扫码分享；覆盖全部成功、有人失败、断网后重试、重新扫码恢复、过期和删除。
5. 优先减少 metadata 无变化写入与重复统计查询；按实际创建、打开、完成、查看结果比例，测每个流程的 D1 读写行数及动态请求数。为账户其他项目与清理任务预留空间后，再决定聚合表是否划算。前端拆包属于后续体验优化；不凭当前低用量或一次本地测试断言可承载多少用户。
