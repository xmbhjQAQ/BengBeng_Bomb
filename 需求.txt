我要做一个无账号、一次性、临时会话式的“绷住挑战”网站(叫“绷绷炸弹”)，核心场景是：用户 A 在 B 站看到一个搞笑或抽象视频，复制视频链接粘贴到网站中，网站解析该视频并获取用于展示和播放的必要信息，包括视频标题、封面、简介、稳定的视频标识、可播放的视频直链以及弹幕数据，A 再填写自己的昵称、可选的接收者昵称以及一段想对对方说的话，点击“生成挑战”后，网站生成一个独立 Challenge，并同时提供一个公开的挑战链接、一张适合直接保存并转发到 QQ/微信的分享图片，以及一个仅供 A 自己保存的私密结果查询入口；分享图片中应包含视频封面、标题、简短简介、发起者昵称、留言、挑战有效期提示和二维码，二维码对应公开挑战链接，朋友可以点击链接或长按图片识别二维码进入挑战；公开挑战链接/二维码本身应尽量设计成一种自包含的 Challenge 凭证，携带创建后基本不会变化且不敏感的信息，例如数据格式版本、视频来源类型、B 站 BV 号及必要的视频标识、发起者昵称、接收者昵称、短留言、创建时间、过期时间、随机 nonce、挑战模式或必要配置等，并由服务器签名以防止篡改，但不要把具有时效性的 B 站 CDN 视频直链、创建者管理 Token、结果查询密钥、服务器 Secret 或其他敏感数据放入二维码中；B 站视频播放地址应在真正需要播放时由后端根据稳定的视频标识重新解析，浏览器获得可用直链后使用网站自己的播放器直接从 B 站 CDN 加载视频，因此视频主体流量尽量不经过网站服务器，弹幕 XML 如存在浏览器跨域问题则可以通过现有轻量后端或 VPS 中转；创建者私密结果入口应使用与公开挑战链接完全不同的 Result/Manage Token，用于查看挑战是否被打开、是否完成、最终是“绷住了”还是“没绷住”、在视频第几秒没绷住，以及主动销毁结果；挑战创建阶段尽量保持轻量和无状态，可以只签发 Challenge Payload，而不必立即建立完整的长期数据库记录，只有接收者真正打开或开始挑战后再根据需要创建临时 Session，完成后保存 Result，这样那些生成后从未被打开的挑战不会产生大量无意义状态；接收者 B 进入挑战后，整个核心体验必须保持在同一个单页中连续推进，不要通过多个页面路由跳转或刷新打断体验，而应通过组件状态切换、过渡动画和统一视觉风格完成整个流程，整体前端希望采用偏 Google Material、圆润、有一定拟物感但不过度复杂的视觉语言；进入挑战后的第一个状态展示视频封面、标题、简介、发起者昵称、留言和挑战基本说明，并简要说明需要使用摄像头的原因、隐私规则和必要免责声明，必须明确告知摄像头画面只在用户浏览器本地用于面部表情检测，不上传、不保存、不做人脸身份识别，但最终的“是否绷住、在哪个时间点没绷住”等挑战结果会返回给挑战发起者，只有用户主动点击“下一步/接受挑战”后才请求摄像头权限；之后进入前置检测状态，调用浏览器端面部检测能力进行人脸存在检查和中性表情校准，用户需要将脸保持在检测范围内，校准完成后显示明确的成功反馈，再由用户点击下一步进入正式挑战；正式挑战开始前，在同一页面中展示一个已经加载好但处于暂停状态的视频播放器，此时用户不能快进、拖动进度、随意 seek、暂停或使用会破坏挑战规则的播放器操作，只允许控制音量和弹幕开关，点击“开始挑战”后播放器进入沉浸式/全屏挑战状态并开始播放，挑战过程中依旧禁止暂停、快进、拖动进度等操作，只保留音量和弹幕开关，右上角显示一个小型摄像头人脸气泡，让用户能确认自己的脸是否处在识别范围内，左上角实时显示当前状态，例如“绷住”“危险”“没绷住”，其中“危险”表示检测到明显笑意但尚未达到最终判定条件；如果挑战过程中检测不到人脸、用户离开摄像头范围、严重遮挡或者无法可靠检测，不要直接判定用户没绷住，而是立即暂停视频，在屏幕中央显示“检测不到人脸”之类的提示，等重新稳定检测到人脸后进行约 3 秒倒计时再继续播放；笑脸检测需要在浏览器本地完成，可以使用已经验证可行的 MediaPipe Face Landmarker 或基于现有实现继续封装，不要把摄像头画面或逐帧表情数据发送到后端，同时不要单纯根据某一帧或固定绝对值判断，要考虑用户自然表情不同的问题、开始前的中性基线、笑容程度连续量化、时间平滑、持续时间和误判恢复等因素，最终输出类似“绷住 / 危险 / 没绷住”的稳定状态；如果检测到用户最终“没绷住”，应立即读取网站播放器当前真实播放时间，记录用户具体在视频第几秒没绷住，停止挑战、退出全屏并进入结算状态，如果用户完整看完视频且始终没有触发判定，则记录为“绷住了”并同样进入结算；结算也尽量在同一个单页内通过状态切换进入，不做整页跳转，绷住和没绷住的结算页面整体结构可以保持一致，都展示视频标题、封面以及相关匿名聚合统计，例如总挑战人数、绷住人数、没绷住人数、没绷住率、平均坚持时间、大家主要在哪些时间点没绷住、没绷住时间分布和热力图等，如果用户没绷住则重点显示“你没绷住了”、具体没绷住时间以及大约超过了多少挑战者，如果用户成功看完则显示“绷住了”；结算页面还应支持生成一个“挑战报告”，可以提供链接和适合转发的图片两种形式，图片中展示结算结果的精简信息，例如视频、是否绷住、坚持时间、主要统计和二维码等，便于分享到 QQ/微信；结算页面底部还需要一个“转发此挑战给朋友”按钮，点击后回到挑战制作状态，并自动预填当前刚刚挑战过的 B 站视频，用户只需要重新填写自己的昵称、接收者昵称和留言即可再次生成新的独立 Challenge；整个产品第一阶段不建立账号体系，不做登录、注册、用户中心、历史挑战列表、好友关系、永久记录等功能，每次分享都是独立的一次性 Challenge/Session，公开挑战凭证和创建者私密结果凭证必须严格分离，挑战本身应有明确有效期，例如未完成挑战在若干小时或若干天后自动失效，完成后的结果再额外保留一段时间供创建者查看，之后自动销毁，创建者也可以通过自己的私密结果入口提前主动销毁挑战结果；如果未来需要公共统计，可以把不同 Challenge 的结果以匿名聚合形式用于计算某个视频的绷住人数、没绷住人数、没绷住率、平均坚持时间、主要笑点和热力图，但不要因此引入账号或暴露私人挑战者身份；部署方面，第一阶段默认优先使用 Cloudflare 的免费资源完成网站主体部署，整体架构应尽量适配 Cloudflare 的 Serverless/Edge 模式，例如前端静态页面和资源部署在 Cloudflare，轻量 API、Challenge 签名验证、B 站播放地址解析、Result 写入读取等逻辑由 Cloudflare 上的服务承担，Session、Result 和匿名统计等小体量结构化数据优先使用适合 Cloudflare 环境的轻量数据库，避免使用高频写入额度较低的存储承担挑战结果数据库；分享图片优先考虑在浏览器本地即时生成，不要为了每张分享图片都增加服务器存储和带宽，B 站视频继续直接由用户浏览器连接 B 站 CDN 播放，不要由 Cloudflare 代理视频主体流量，摄像头和笑脸检测同样完全留在客户端，从而让 Cloudflare 主要承担静态资源、少量 API 请求和轻量数据库访问；现有用于解决 B 站弹幕 XML 跨域或其他必须中转的轻量 VPS 服务可以暂时独立保留，不要求为了架构统一强行迁移到 Cloudflare，但应保持接口简单并避免让视频流量经过该 VPS；设计 API 时不要让前端高频上传 Smile Score，也不要通过高频轮询结果页面制造大量无意义 Worker 请求，一次完整挑战原则上只产生少量必要的动态请求；整个部署设计首先以 Cloudflare Free 能长期支撑个人项目为目标，同时代码和数据层应保持容易升级到 Cloudflare 付费计划或替换单个组件，而不是依赖某个免费额度写出无法扩展的特殊实现；整个项目是个人娱乐性质项目，目标是好玩、轻量、能顺畅在桌面和手机浏览器使用，并尽量减少不必要的后端状态和复杂基础设施，具体前端框架、数据库结构、Challenge Payload 编码签名方式、Session 结构、播放器内部封装、Cloudflare 各产品之间的具体职责等可以由你结合当前实际代码和最新平台能力自行分析后决定，但请始终围绕上述产品交互、一次性临时挑战逻辑以及“重计算留在客户端、视频流量留在 B 站 CDN、网站后端保持轻量”的原则实现，不要擅自把它扩展成重账号、重社区或大型商业平台。

开发请尽量模块化，不要把一堆东西塞到一个文件里，写代码要积极写注释，尽量提升代码可读性。变量名要规范，双端兼容性要强。
参数尽量配置文件化，包括但不限于后端endpoint，key，面部判定灵敏度等各项数据。省的到时候需要改参数的时候在一堆文件代码里到处找。不过也要注意安全问题，Cloudflare Secret、签名密钥、后端鉴权 Key 这类必须走环境变量 / Secret，不能写进仓库，更不能下发给浏览器！！！安全第一！！！
